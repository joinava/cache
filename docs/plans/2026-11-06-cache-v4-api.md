# Cache v4: independent bulk reads and automatic batching

Status: approved. Package implementation and verification are in progress. Consumer migration and production validation remain open.

## 1. Problem and success criteria

Callers have two distinct needs: read a known set, and combine independent calls for throughput. The current API couples these needs to method names.

`Cache.get` can join automatic store batches. `Cache.getMany` bypasses that queue. Producer wrappers require callers to assemble producer batches themselves. That accumulation can delay store reads that could already run.

V4 separates request shape, automatic batching, and failure handling. Breaking changes are allowed.

Success means:

- Callers can submit one resource or a known set with either batching policy.
- Bulk-capable stores and producers use automatic batching by default.
- Single-only implementations receive work promptly, without an accumulation window.
- Bulk reads preserve successful slots when other slots fail.
- Store reads start before producer batch accumulation.
- Cancellation removes queued participation without cancelling other callers' dispatched work.
- Types preserve resource-specific inference and heterogeneous tuple positions.
- Diagnostics distinguish logical reads, queue wait, and dispatched work without unbounded metric tags.
- The migration deletes redundant wrappers and duplicate store read implementations.

This plan defines the initial v4 release. The user authorized implementation and pull request preparation. Publication and deployment require separate authorization.

## 3. Ownership and scope

The cache package owns resource identity, freshness classification, request scheduling, producer sharing, result assembly, and persistence observation.

Stores own physical reads and writes. Producers own resource production. Consumers own whether partial results are useful and whether persistence must finish before proceeding.

Reuse these existing owners:

- Evolve `Store` and its result types in `src/types/06_Store.ts`.
- Consolidate cache reads in `src/Cache.ts`.
- Evolve `src/utils/storeReadBatcher.ts` for store scheduling.
- Evolve `collapsedTaskCreator.ts` and wrapper orchestration for producer sharing.
- Reuse PR #19’s `src/utils/pendingResources.ts` for entries with pending writes. Extend it to both v4 call shapes; do not replace it with longer-lived producer invocations.
- Extend adapters in `src/utils/utils.ts` before adding another adapter module.
- Retain identity translation in `wrapHashedInputProducer.ts`.
- Retain producer result normalization and resource helper ownership.

Do not introduce another cache implementation or a compatibility wrapper layer.

The initial release excludes aborting dispatched shared operations when all callers cancel. It also excludes mutation ordering queues and new distributed invalidation guarantees.

Existing resource formats, variant matching, freshness directives, supplemental produced resources, store writes, and lifecycle policies remain package responsibilities. Their semantics must survive the refactor.

## 4. Public read contracts

The following signatures show contract shape. Implementation must retain the package's resource registry generics and positional mapped types.

### Store capabilities

A Store declares exactly one read primitive, alongside its existing write and lifecycle operations:

```ts
type Reader<Request, Entry> =
  | {
      get(
        request: Request,
        options?: { signal?: AbortSignal },
      ): Promise<Entry[]>;
      getMany?: never;
    }
  | {
      get?: never;
      getMany(
        requests: readonly Request[],
        options?: { signal?: AbortSignal },
      ): Promise<(Entry[] | Error)[]>;
    };
```

Bulk output length and order must match input length and order. Each slot contains matching entries or an Error. An empty entry array is a successful store read.

A store may reject its whole operation when it cannot provide partial results. Non-Error thrown values become Errors with the original value as their cause.

Require exactly one primitive in TypeScript. Validate that requirement at runtime when constructing a Cache, so JavaScript callers cannot supply both or neither.

Built-in choices:

| Store         | Primitive | Reason                                          |
| ------------- | --------- | ----------------------------------------------- |
| MemoryStore   | `get`     | Accumulation adds latency without reducing I/O. |
| PostgresStore | `getMany` | Bulk SQL reduces database roundtrips.           |
| SqliteStore   | `getMany` | Bulk work reduces database and worker requests. |

Preserve cooperative fairness when adapting large MemoryStore groups. Bounded concurrency alone does not guarantee event-loop fairness.

### Built-in store partial results

PostgresStore and SqliteStore preserve complete successful request slots when another request or SQL chunk fails. Retain the existing query strategy and concurrency. Do not retry failed chunks as individual queries.

- A request encoding, entry decoding, or variant-matching failure becomes an Error in each affected request slot. If one required variant fails, fail the request instead of returning an incomplete variant list.
- A SQL chunk failure becomes an Error in every request slot served by that chunk. Preserve successful chunks and continue requesting subsequent chunks.
- Caller cancellation stops further chunk dispatch and rejects the call.
- A known lifecycle failure that prevents dispatch, such as store closure or worker termination, stops further chunks. Preserve completed results when the Store can assemble them; mark remaining slots with the failure. If a worker failure loses all intermediate results, reject the whole operation.
- Initialization or connection acquisition failure before usable results are available may reject the whole operation. Internal contract violations reject the call.

Do not classify ordinary SQL errors to decide whether subsequent chunks are worth attempting. Continuing means completing the original request, without retries or increased concurrency.

Store reads return one promise for the complete positional array, without streaming. Successful internal SQL chunks remain unavailable to the caller until that Store invocation settles. Independent Store invocations can settle separately and feed ready work to production. Postgres currently gathers sequential query chunks before assembling request results. Change that assembly to preserve chunk failures and request decoding failures. SQLite must carry partial chunk outcomes through its worker protocol; main-thread decoding alone cannot preserve results lost inside the worker.

### Raw store adapters

Export `getOne(store, request, options)` and `getMany(store, requests, options)`. Keep these adapters in the existing utility module.

`getOne` calls the single primitive, or unwraps one bulk slot. An Error slot rejects the scalar call.

`getMany` calls the bulk primitive, or uses bounded-concurrency single reads. Single-read failures become individual Error slots. If the bulk primitive rejects with an operational read failure, return that Error in every affected slot. Preserve the same Error instance across those slots. Wrap non-Error failures once with their original value as the cause.

Cancellation and contract violations, including an incorrect positional result count, reject the adapter call. The adapter validates the positional contract before returning results. Empty requests resolve to an empty array without dispatch.

This contract is independent of the Store’s read capability. Cache uses the same failure conversion instead of implementing a second fan-out policy. Scalar adapters and Cache reads reject when their single slot contains an Error. Diagnostics count one failed underlying operation separately from the number of affected request slots. Evolve `naiveGetMany` rather than maintaining two single-to-bulk implementations.

These adapters do not accumulate independent calls. Store authors and direct store callers can use them without constructing a Cache.

### Cache reads

```ts
type ReadOptions = {
  signal?: AbortSignal;
  autoBatch?: false;
};

cache.get(request, options); // Promise<LookupResult>
cache.getMany(requests, options); // Promise<positional LookupResult | Error slots>
```

Both methods use the same normalization, dispatch, classification, and diagnostics path. Implement scalar reads through the common path and unwrap their single slot.

`LookupResult` retains existing hit, miss, freshness, and variant information. A cache miss is a successful lookup result, not an Error.

A whole store failure becomes an Error in every affected public bulk slot. Caller cancellation rejects the public call. A store contract violation, such as an incorrect result count, also rejects the call.

Export `throwIfAnyError(results)` for callers that require all results. It returns the success-only positional type or throws the first Error in input order. All results settle before this helper runs. It does not imply rollback or a transaction.

Empty bulk calls resolve to an empty array without dispatching work.

## 5. Automatic batching

`autoBatch` controls accumulation across calls. It does not control whether a known set uses a bulk primitive.

```ts
await cache.getMany([a, b, c], { autoBatch: false });
// Dispatch the supplied set promptly through store.getMany([a, b, c]).
// Do not wait to combine it with another call.
```

| Capability  | Omitted `autoBatch`                                           | Explicit `false`                         |
| ----------- | ------------------------------------------------------------- | ---------------------------------------- |
| Single-only | Dispatch promptly; adapt known sets with bounded concurrency. | Same behavior.                           |
| Bulk-only   | Accumulate compatible pending reads.                          | Dispatch the current known set promptly. |

Only `false` is accepted as an explicit participation value. Reject `true` in TypeScript and at the public runtime boundary. Omission always selects the capability-driven default. Neither Cache construction nor wrapper construction can override default participation.

Cache construction accepts `readBatching` settings for store read accumulation. Wrapper construction accepts separate `producerBatching` settings for producer accumulation. Neither option accepts `false` or controls default participation. Remove the old `batchReads` construction option in v4. Store write batching is outside this change.

Both settings use the existing scheduler configuration shape:

```ts
type BatchingOptions = {
  maxBatchSize?: number;
  batchScheduleFn?: (dispatch: () => void) => void;
};

const cache = new Cache({
  store,
  resourceTypes,
  readBatching: { maxBatchSize: 20 },
});

const client = wrapProducer({
  cache,
  produceMany,
  producerBatching: { maxBatchSize: 20 },
});

client.getMany(requests, {
  autoBatch: { store: false },
});
```

The example disables store accumulation for this call. Producer accumulation retains its capability-driven default. `readBatching` belongs to the Cache instance; `producerBatching` belongs to the wrapper instance. The queues remain independent.

Use a default maximum batch size of 20 for each queue. Use the current store scheduling convention: dispatch after Promise continuations. A custom `batchScheduleFn` replaces that scheduling convention for its own queue. Single-only implementations do not accumulate calls, regardless of supplied scheduler settings. Per-call options control participation, not scheduler configuration.

A known set can join other pending reads when automatic batching is enabled. Batch limits may split that set. With `autoBatch: false`, the batch limit does not apply: the known set reaches the Store or producer as one invocation. No read method promises a transaction or a common database snapshot.

Store batching must preserve each request's parameters and independent freshness classification. Do not collapse store requests merely because their IDs match.

## 6. Producer wrappers

Keep two factories for the two identity models:

- `wrapProducer`: the caller already has a resource ID.
- `wrapHashedInputProducer`: the package derives the ID from the original input.

Each factory returns an object with `get` and `getMany`. Remove separate bulk wrapper factories after migrating their callers.

Declare producer capability at the top level:

```ts
wrapProducer({
  cache,
  produce(request) {
    /* single-resource production */
  },
  // produceMany?: never
});

wrapProducer({
  cache,
  produceMany(requests) {
    /* positional production results */
  },
  // produce?: never
});
```

The options type is a union that requires exactly one producer primitive. Apply the same structure to hashed-input producers. Validate the choice at the wrapper boundary for JavaScript callers.

For typed hashed-input helpers, retain the existing branch descriptor returned by `.build()`. Accept a single-capability descriptor under `produce` and a bulk-capability descriptor under `produceMany`. Each field accepts either its ordinary callback or its matching typed descriptor. Reject a descriptor whose capability conflicts with its field. Do not retain a separate `hashedInputProducer` option or change helpers into spreadable callable bundles in v4.0.

```ts
wrapHashedInputProducer({
  cache,
  produce: hashedInputProducerByInputType(/* branch declarations */).build(),
});

wrapHashedInputProducer({
  cache,
  produceMany:
    bulkHashedInputProducerByInputType(/* branch declarations */).build(),
});
```

Descriptors retain per-branch input/output relationships, minted ID types, coverage metadata, and runtime branch tables. Preserve registry compatibility checks, minted-ID checks, supplemental-input routing, and bulk grouping. Direct callback declarations continue to supply `hashInput` separately. Descriptor declarations carry their own branch hash functions and must not accept a conflicting separate `hashInput`.

Retain existing normalized producer result semantics, including supplemental resources. Bulk producers return one primary result or Error per request. Supplemental resources can be stored without adding public result slots.

Every producer request is independent. A request’s result must remain valid when other requests are added, removed, reordered, split into other batches, or deduplicated. Bulk producers may share physical work across requests, but must not require the caller’s original batch membership. Each returned slot corresponds to its own request. Document this contract on producer types, wrapper factories, and typed dispatch helpers.

Wrapped call options separate the store and producer policies:

```ts
type WrappedReadOptions = {
  signal?: AbortSignal;
  autoBatch?: {
    store?: false;
    producer?: false;
  };
  onStore?: (stored: Promise<void>) => void;
};

client.get(request, options);
client.getMany(requests, options);
```

Each omitted field uses its capability-driven default. Single producers run promptly. Bulk producers accumulate compatible pending misses by default.

For a bulk-capable producer, the two modes have different readiness rules:

- With `autoBatch.producer: false`, finish classifying the known set’s eligible Store reads before dispatching its complete production cohort. Include misses, read-failure fallbacks, bypass requests, and stale-while-revalidate refreshes. Send the cohort as one bulk invocation, whatever the batch limit, without waiting to accumulate other calls. Refreshes in the cohort keep their obligation when the caller cancels.
- With `autoBatch.producer` omitted, submit each ready production request to the producer queue as its Store classification completes. Bypass requests can enter immediately. Do not wait for unrelated Store chunks or the rest of the known set. The scheduler may combine these requests with other calls. Readiness is observed when an independent Store invocation settles, not as its internal SQL chunks complete.

Explicit `autoBatch.producer: true` remains invalid. A single-only producer dispatches each ready request promptly and does not acquire a whole-set classification barrier.

If a caller with `autoBatch.producer: false` joins compatible production already queued for automatic batching, dispatch that shared request immediately instead of inheriting the existing queue delay. Remove it from the automatic queue so its later scheduled callback cannot dispatch it again. Preserve all attached callers and their persistence associations. Other queued requests keep their schedule. Already-dispatched shared production is joined without restarting it. This may reduce the automatic caller’s batch size; honoring the direct caller’s opt-out takes priority. For a known-set direct call, apply this rule once its complete production cohort is ready under the classification barrier above.

Background revalidation does not delay a stale response. Under automatic batching, it follows the producer queue. With `autoBatch.producer: false`, it joins the call's single cohort invocation.

Retain the existing typed ID/input dispatch helpers. Evolve their contracts where necessary; do not create another identity router.

## 7. Execution and sharing

```text
Caller submits one request or a known set
+-- Normalize identity, parameters, and directives
+-- Consult pending-write entries using current request freshness and variant rules
+-- Start Store reads for every non-bypass request; merge persisted and pending candidates
|   +-- Optional store accumulation
|   +-- Dispatch and classify each result
+-- Settle usable-hit slots internally
+-- Send misses, bypasses, and revalidation work to production
|   +-- Join compatible pending production
|   +-- Optional producer accumulation
|   +-- Dispatch, normalize, and assemble positional results
+-- Start produced-resource writes
+-- Await all public result slots; return one array and hand foreground persistence to onStore
```

Start eligible Store reads without waiting for producer accumulation. Individual hit slots settle internally without waiting for unrelated production. A scalar hit can return immediately. A bulk public promise still waits for all its slots and returns one positional array; it does not stream partial results. Writes remain independently observable through `onStore`. Cancellation or a contract violation can reject the public call before all internal work settles.

Producer sharing applies to compatible individual requests. For `[A, B]` and `[B, C]`, both callers can share pending production for B.

Producers continue receiving original parameter values. Define sharing identity from the completed request and successfully normalized parameters, because normalization promises equivalent producer behavior. Different original forms that normalize identically may share production. Include resource identity and directives that affect production. Validators are not currently producer inputs; do not add validation inputs as part of this refactor. If a future contract supplies validators, include them in compatibility then. ID equality alone is insufficient. Scope sharing to one wrapper instance. Hashed requests retain original inputs until production no longer needs them. Call-specific signals and `onStore` callbacks are observers, not producer-input identity.

Producer sharing ends when production settles, independently of persistence. The current implementation removes completed tasks immediately; it has no post-completion collapse window. Retain `collapseOverlappingRequestsTime` and its existing default of 3 seconds. A caller arriving after that limit cannot join the older invocation, even if it remains pending.

After production succeeds, PR #19’s pending-write overlay covers the interval until persistence settles. Register normalized primary and supplemental entries without a visibility gap before delivering the produced result. Recheck variant matching and freshness against each new request at lookup time. Pending entries participate in the canonical Cache lookup structure, including fresh, stale-while-revalidate, and stale-if-error outcomes. Reuse the Cache’s classification and candidate-selection rules, including tie handling; do not maintain a separate overlay freshness interpreter. The overlay models all retention-eligible pending resources, not the exact subset a backing Store will retain. Stores may retain a subset, including one entry per ID-and-variant slot. Do not discard an otherwise eligible pending candidate merely because a Store may choose another candidate for that slot. Bypass requests skip the overlay; entries with no retention eligibility, including `storeFor: 0`, are not overlay candidates.

PR #19’s approved scope now includes stale pending entries; the earlier fresh-only proposal is superseded. Consult the Store even when a pending entry is fresh. Combine persisted and pending candidates using the same canonical classification, priority, birth-date selection, and tie rules. A pending fresh entry must not hide a better persisted candidate. Preserve pending candidates across the Store read so a read snapshot taken before a write completes cannot lose the entry when overlay cleanup runs before the read returns. Preserve `onCacheReadFailure` handling for normalization failures on pending-entry paths. The PR #19 integration must verify these source-merging and settlement-race contracts before v4 adopts its implementation.

Retain each candidate’s associated write promise. Multiple overlapping writes and variants must remain distinguishable. Remove each candidate when its own write succeeds or fails. Cleanup of an older write must not remove a newer candidate. A failed write must not pin an entry. The overlay remains local to one wrapper instance and does not impose ordering on concurrent writes.

A returned overlay entry supplies its own pending persistence through `onStore`, including when returned stale or as a stale-if-error fallback. A refresh started in the background is a separate write dependency and is excluded for the caller that receives stale data. The joining age limit applies to unfinished production, not to overlay entries. Overlay eligibility comes from current freshness and variant checks. Do not retain completed freshness decisions or entries after their writes settle.

Do not force wrapper results into original producer batch groupings. Track each request's production and associated writes directly. Reuse normalization helpers for assembly.

Retain the existing wrapper policy `onCacheReadFailure: "call-producer" | "throw"`, with `"call-producer"` as the default. A failed store read therefore falls back to production by default. With partial store results, apply this policy only to failed slots and preserve successful lookups. Under `"throw"`, scalar calls reject and bulk calls return the read Error in the affected slot. Cancellation and contract violations reject the public call instead of triggering production.

Freshness behavior remains explicit: bypass reads skip the store; stale-while-revalidate can return stale data while production runs in the background. Stale-if-error applies per request. An empty successful store read does not prove that the source resource does not exist.

### Overlapping timeline

1. At t=0, caller X submits `[A, B]`; both store reads enter the store queue.
2. At t=1, caller Y submits `[B, C]`; compatible store work can share a dispatched bulk operation without merging request semantics.
3. The store returns a hit for A and misses for B and C.
4. X receives no final bulk array until its required slots settle. A does not enter production.
5. B and C enter the producer queue. Both callers attach to the same compatible pending production for B.
6. Y cancels while production is queued. C leaves the queue if Y was its only participant. B remains because X needs it.
7. Production for B dispatches. X later cancels; its wait rejects, but dispatched production continues.
8. After B is produced, an immediate repeat can use its fresh pending-write entry until the write settles. Its `onStore` observes that write. Later calls use the Store after overlay cleanup.

## 8. Cancellation and failure boundaries

A known-set call has one caller signal for the entire set. Cancellation rejects that caller's public promise.

Before dispatch, remove cancelled participation. Remove a queued request when no interested participants remain. Preserve requests that another caller still needs.

After dispatch, cancellation stops only the caller's wait. It cannot remove items from an operation already running.

A stale-while-revalidate call accepts a background refresh before returning its stale result. That accepted refresh remains queued even after the initiating call completes. The queue tracks that background obligation separately from callers waiting for fresh results. The application closes wrappers before their Cache, as defined in the shutdown section.

A caller that later needs fresh data may join that compatible refresh. For this caller, production and its writes are foreground work. For the caller that already received stale data, the same work remains background work. Cancelling the new caller must not remove the accepted background refresh.

Do not abort shared store or producer operations, even when all participants cancel. Do not pass one participant's signal into shared work.

An exclusively owned direct store operation may receive its caller's signal. Automatic batching and producer sharing must track operation ownership explicitly. Disabling accumulation does not disable producer sharing.

Observe every dispatched promise and release abort listeners after completion or cancellation. Background failures must use existing error reporting, without unhandled rejections.

Preserve Error identity for per-entry failures. Whole-operation failures fan out to affected slots. Contract violations reject the call instead of pretending to be resource failures.

Treat arbitrary errors thrown by custom Stores and producers as operational failures. Do not infer contract violations from error classes or message text. Package-detected violations include invalid capability declarations, invalid public requests, uncovered resource types, and malformed positional results. Give package-detected contract violations a recognizable internal category so failure conversion and producer fallback preserve their rejection. Validate before dispatch where possible. Cancellation remains a separate public-call rejection.

## 9. Persistence observation

Retain `onStore(stored: Promise<void>)` as the persistence hook. Do not restore `waitForStore` or `StoreOutcome`.

Invoke the hook once for a successfully completed wrapped call. The promise covers that call’s foreground stores, including writes shared through pending production and writes associated with pending-overlay hits. Foreground ownership depends on the result this caller consumes, not on the invocation’s original trigger.

Wait for every foreground store to settle before rejecting the aggregate promise. Report the first failure in stable request order. A call with no foreground writes receives a fulfilled promise.

Read and production failures do not become persistence failures. A refresh write is excluded for a caller that returned stale data. The same write is included for a caller that waits for the refreshed result, including when it joins an invocation originally triggered as background revalidation.

Observe write failures immediately, including when the caller ignores the hook. A synchronous hook throw rejects the wrapped call. The wrapper does not await a returned callback promise. A cancelled or rejected wrapped call need not invoke the hook.

Callers own persistence deadlines and failure policy. Preserve Ranker's bounded best-effort wait and HHAX's required bounded persistence wait during migration.

## 10. Diagnostics and rollout evidence

Route direct and automatic reads through the same dispatch instrumentation. Evolve the diagnostics work in cache PR #25 rather than adding competing event families.

Separate these observations:

| Observation                        | Calculation and scope                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Logical read duration and count    | Public read start to settlement; count resource slots separately from API calls.                        |
| Queue wait                         | Enqueue to dispatch for participating store or producer work. Direct work has no accumulation wait.     |
| Store operation duration and count | Actual Store primitive dispatch to settlement, including whole-operation failure.                       |
| Producer duration and count        | Actual producer dispatch to settlement, separate from caller wait.                                      |
| Batch size and returned entries    | Dispatched requests and returned entry counts; distinguish entry failures and whole-operation failures. |
| Caller failures and cancellations  | Count affected logical requests separately from failed underlying operations.                           |

Measure byte size only where an existing encoding or transport provides it. Do not serialize values again to measure size.

Monorepo metric tags must use bounded cache names, operation kinds, store kinds, services, and outcomes. Keep cache keys and resource/patient IDs out of tags. Use existing deployment correlation for release comparisons.

Package diagnostics do not measure database pool wait or individual SQL executions. Use database instrumentation for those measurements. One Store invocation can issue several SQL queries.

Before rollout, inventory existing event-loop, read-latency, database-volume, database-latency, and pool-wait measurements. Wire missing low-cardinality metrics and Pulumi dashboard/monitor definitions in the consumer migration.

Use baseline distributions and service objectives to choose alert thresholds. Do not invent thresholds in the library. Any expensive temporary dimensions require a simultaneous removal PR, as previously requested.

## 12. Mechanism counterfactuals

These are design regression scenarios, not claims of production incidents.

| Mechanism                        | Before                                                                | Expected v4 outcome                                            |
| -------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------- |
| Independent `autoBatch`          | A known-set caller must bypass global accumulation.                   | The known set can join other pending reads.                    |
| Capability-driven defaults       | A memory-only read can wait for ineffective batching.                 | Single-only reads dispatch promptly.                           |
| Partial bulk errors              | One failed entry loses successful cache results.                      | Successful slots remain usable.                                |
| Separate stage queues            | Caller accumulation can postpone cache reads.                         | Store reads run while producer work accumulates.               |
| Per-request production sharing   | Overlapping batches can produce B twice.                              | Compatible pending B production runs once.                     |
| Participation cancellation       | A queued cancelled request wastes capacity or cancels another caller. | Remove only unused queued work; retain shared dispatched work. |
| Foreground persistence aggregate | An early failure can hide stores still running.                       | The persistence promise settles after every foreground store.  |
| Common diagnostics               | Direct and automatic paths can report different operation coverage.   | Every physical Store dispatch has one operation observation.   |

## 13. Rollout, rollback, and review assumptions

Publish v4 only after package gates and independent review pass. A major version makes the migration explicit. Do not silently upgrade consumers.

Complete the consumer inventory before publication. Release the package first, then migrate the monorepo through its normal PR and deployment process. These are separate repositories, not stacked PRs.

Compare the deployed v4 cohort with a representative pre-deploy baseline. Inspect read tails, event-loop delay, pool wait, database query volume, producer volume, failures, and persistence timeouts.

Performance acceptance requires no material regression against existing service objectives and the measured baseline. Package tests establish semantics; production measurements establish workload effects.

Rollback the consumer dependency, lockfile, and API migration together. No database migration or stored resource format change should be required. Leave v4 published; do not repoint or unpublish a released version.

Review these explicit assumptions before implementation:

- Both queues default to a maximum batch size of 20 and the current store scheduling convention.
- Capability alone determines default participation. Callers can only disable accumulation, using `false`.
- `autoBatch` disables accumulation only; it does not disable compatible pending producer sharing.
- Pending producer sharing retains the existing joining age limit, with a default of 3 seconds. Completed results have no additional collapse window.
- Both wrapper identity models remain useful and retain separate factories.
- No global mutation ordering is added. Callers must await writes when later operations depend on them.

The review should approve or amend these contracts before implementation starts. Implementation must update this plan when an approved decision changes.

## 14. Approved shutdown design and v4.1 follow-up

### Approved v4.0 wrapper lifecycle

Each returned wrapper client exposes `close(): Promise<void>` alongside `get` and `getMany`. Wrapper close takes no timeout. It rejects new calls, flushes producer queues without accumulation delay, and drains accepted pipelines, background refreshes, and their writes. Accepted reads may still lead to production and persistence while the wrapper drains. Repeated close calls observe the same underlying drain.

The application closes all wrappers before closing their shared Cache. It keeps producer dependencies available until wrapper shutdown completes, and closes externally owned database pools after Cache shutdown. The Cache does not register wrappers for automatic shutdown.

Cache close drains accepted Store operations before invoking Store cleanup. Preserve after-close policies for new public Cache operations; accepted internal operations remain permitted to finish. Wrapper admission closes independently, so no new wrapped calls are accepted after wrapper close starts. Already-accepted reads may still start production and writes while the wrapper drains.

### V4.1 follow-up: bounded shutdown with abandonment

Add explicit bounded shutdown that attempts cancellation where supported, stops queued work, and prevents abandoned producer completions from starting new writes. Already-dispatched operations may still run. Define caller settlement, background refresh cleanup, Store ownership, and safe dependency shutdown before adding the timeout API. A timeout must do more than stop waiting. This is a follow-up, not v4.0 scope.

### Approved v4.0 Cache and Store lifecycle

`Cache.close(): Promise<void>` and the generic `Store.close(): Promise<void>` take no timeout. Cache drains accepted Store operations before closing the Store. Store close releases its owned resources to completion. Remove implicit disposal deadlines from Cache and Store implementations, including the current 60-second Cache and SQLite async-disposal deadlines. SQLite’s existing timeout destroys workers; remove that timeout path from v4.0 graceful close rather than preserving forced cleanup implicitly.

The application owns the process shutdown deadline. Reaching that deadline does not make dependencies safe to close or establish graceful completion. Coordinated cancellation, abandonment, and forced cleanup remain v4.1 scope.

### Shutdown failure reporting

Shutdown guarantees lifecycle completion, not operation success. Read and producer failures remain attached to call results and diagnostics. Persistence failures remain attached to `onStore` and diagnostics. None of these operational failures independently makes `close()` reject. A failed operation is settled work and must not stop the drain.

`close()` rejects when draining itself or owned-resource cleanup fails. Attempt all required cleanup even after a lifecycle failure. Preserve multiple lifecycle failures in an `AggregateError`. A successful close means accepted work has settled and owned resources have been released; it does not guarantee successful persistence. Callers requiring successful persistence must observe `onStore`, including before shutdown. Do not retain historical operation failures for shutdown to replay.

Raw bulk adapter failure conversion, normalized producer-input compatibility, producer request independence, and scheduler defaults are approved. Operational read failures become positional Errors; cancellation and contract violations still reject. Both queues default to 20 requests and retain the current dispatch logic.

Exact registry generics, type-test harness reuse, consumer inventory, metric names, and baseline-derived alert thresholds require engineering verification. They are implementation preparation, not additional caller-policy decisions.

## 15. Follow-up: producer batching by resource type

Multi-resource-type producers may need a different maximum batch size and accumulation time window for each resource type. V4.0 uses one `producerBatching` configuration per wrapper. Do not add per-resource-type configuration in this implementation.

A follow-up must define how per-type limits interact with producers that efficiently handle mixed resource types in one invocation. Preserve independent request semantics, positional assembly, sharing, cancellation, and shutdown. Distinguish the accumulation window from `collapseOverlappingRequestsTime`, which controls joining pending production. Choose whether limits belong to typed branch declarations or a wrapper scheduling policy before implementing this extension.

## 16. Approved event-emitter removal

V4 removes `Cache.emitter` and its `store` event. Store diagnostics use the existing `cacheStoreEntryChannel`; no replacement event emitter is introduced.

Producer diagnostics require `failedRequestCount`. Resolved bulk invocations count Error slots while retaining `outcome: "success"`. Whole rejection or contract failure counts every request. Scalar success reports zero; scalar failure reports one.

## 17. Approved Store-read channel rename

V4 renames `@zingage/cache:read-batch` to `@zingage/cache:read-store`. Its exports become `CACHE_READ_STORE_CHANNEL_NAME`, `cacheReadStoreChannel`, and `CacheReadStoreMessage`. This breaking change provides no old-name aliases. PR #25 retains the v3 names.

The channel reports each physical Store read, including single reads, direct bulk reads, and automatic bulk reads. The rename does not change payload fields or timing semantics.
